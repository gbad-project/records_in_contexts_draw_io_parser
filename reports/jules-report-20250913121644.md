**Date:** 2025-09-13

**Subject:** Analysis and Enrichment of Task `P4T2 – CSV → RDF triple conversion`

## 1. Objective

My primary objective was to select one complex, unreviewed task from the implementation plan in `AGENTS.md` and enrich its description. The goal was to scrutinize the existing legacy Python codebase to provide a highly detailed, actionable, and unambiguous set of instructions for the AI agent that will ultimately implement the task.

## 2. Task Selection

I selected **P4T2 – CSV → RDF triple conversion** for enrichment. I identified this task as the most complex and critical piece of the new pipeline. It represents the core logic of the data transformation, replacing the existing RML-based engine, and its success is pivotal for the entire project.

## 3. Analysis of Legacy Codebase

To gather the necessary details, I performed a thorough review of three key Python scripts from the legacy implementation:

### 3.1. `map_rml.py`

- **Finding:** This script does not contain the core mapping logic. It acts as a wrapper that invokes an external Java-based RML processor (`rmlmapper.jar`) to perform the actual CSV-to-RDF conversion.
- **Key Insight:** This clarified that P4T2 is not a task of "porting" Python logic, but of **building a new mapping engine from scratch** in TypeScript to replace the functionality of the RML processor.
- **Post-processing:** The script contained a crucial `postprocess` function. I identified the `remove_shorter_duplicate_labels` function as the "first round post-processing" step mentioned in the original task description. The specific algorithm for this function was extracted to be included in the new task description.

### 3.2. `map_schema.py`

- **Finding 1 (Preprocessing):** This script contains extensive and complex CSV preprocessing logic (`add_preprocess`, `auth_preprocess`). It heavily transforms the source CSV by splitting columns, creating new columns based on conditional logic, and deriving new values.
- **Key Insight:** The P4T2 mapper will not receive raw CSV data. Its input will be the wide, heavily-processed data structure that results from these preprocessing steps (which are to be ported in task P3T1). This understanding is critical for defining the mapper's input contract.
- **Finding 2 (RML Generation):** The script also generates the `.rml` files that the Java mapper consumes. Analyzing this RML generation logic revealed the complexity of the mapping rules.
- **Key Insight:** The new TypeScript mapper must support advanced features like conditional triple generation (based on non-null values or regex matches, mimicking the `FnO` logic) and joins between mapping rules (`rr:parentTriplesMap`).

### 3.3. `draw_io_parser.py`

- **Finding:** This script parses the Draw.io XML into a structured format. The key output is a dictionary, referred to as `blocks`, which organizes all RDF types and properties by their subject identifier.
- **Key Insight:** This `blocks` dictionary is the direct conceptual blueprint for the `MappingModel` that will be the primary input to the P4T2 mapper. This allowed me to define the expected structure of the `MappingModel`: a collection of `TriplesMap` objects, each containing rules for a subject, its types, and its predicate-object maps.

## 4. Summary of Enrichment to `AGENTS.md`

Based on the insights above, I replaced the original high-level description of P4T2 with a detailed, step-by-step implementation guide. The new description includes:

- A clear **Goal** stating that a new engine must be built.
- A precise **Function Signature** and definition of **Inputs**.
- A **Core Implementation Steps** section that provides a clear algorithm for the `mapCsvToRdf` function, including how to iterate, generate subjects, handle types, and conditionally generate objects based on various mapping rules (references, templates, joins).
- A detailed **Post-processing Integration** section that specifies the exact algorithm for `remove_shorter_duplicate_labels` to be ported.
- A `<!-- reviewed -->` tag to mark the task as analyzed and enriched.

This detailed plan will significantly de-risk the implementation of P4T2 by providing the assigned agent with a clear, well-defined, and actionable set of instructions.
