## 2. Analysis Process

My analysis followed a three-pronged approach: reviewing the source code, examining the test suite, and defining the data contract by inspecting input and output files.

### 2.1. Source Code Analysis

I performed a deep dive into the relevant Python scripts to deconstruct the logic that P3T1 requires porting to TypeScript.

-   **`map_schema.py`**: This script acts as the orchestrator. It dispatches to different preprocessing functions (`add_preprocess`, `auth_preprocess`, `generic_preprocess`) based on a `schema_code`. The core logic for transformation is contained within these functions.
-   **`gbad/converter/preprocessors.py`**: This file contains the essential `SourceCSVPreprocessor` class. I determined that this class is the workhorse of all transformations, providing methods for loading data, splitting columns based on a given transformation function (`column_split`), and adding new columns to the dataset. Understanding this class was critical to understanding the entire preprocessing workflow.

### 2.2. Test Suite Reverse-Engineering

The goal was to reverse-engineer the success criteria for P3T1 from its tests.

-   **Unit Tests (`tests/test_map_schema_generic.py`)**: My analysis revealed that the unit tests are insufficient. They only cover the `generic` schema, which involves no actual data transformation, and merely assert that an RML file is created. This is a key finding: **the core preprocessing logic is not unit-tested**.
-   **Integration Tests (`tests/scripts/linux/test_add.sh`, `tests/scripts/linux/test_auth.sh`)**: These scripts, while not performing any validation, were crucial. They revealed the exact test data files used for the `add` and `auth` pipelines, pointing me to `test_description_tailshuf_100.csv` and `test_authority_tailshuf_100.csv`.
-   **Discovered Bug**: I noted that the file paths within these shell scripts are incorrect (e.g., `tests/test_...` instead of the correct `gbad/mapping/source/tests/test_...`).

       - Updating records from an external data source.
       - A generic `columnSplit` function that takes a source column name, a list of new column names, and a transformation function. This function should apply the transformation to the source column for each record and populate the new columns.

   - **AICODE-TODO: P3T1.2 - Implement the `add` Schema Preprocessing Pipeline.**
     - This pipeline transforms data for "Descriptions and Listings".
     - **Column Splits**: Implement the following transformations, using the utility from P3T1.1:
       1.  `FINDAID:FINDAIDLINK:FINDAID_URL` -> `FINDAID`, `FINDAIDLINK`, `FINDAID_URL`. Logic: split by ` : `.
       2.  `IIL:IIL_URL` -> `IIL`, `IIL_URL`. Logic: split by ` : `.
       3.  `INDEXPROV` -> `INDEXPROV_1` to `INDEXPROV_30`. Logic: split by adjacent-case (e.g., `FirstSecond` becomes `["First", "Second"]`).
       4.  `INDEXNAME` -> `INDEXNAME_1` to `INDEXNAME_30`. Logic: split by adjacent-case.
       5.  `INDEXSUB` -> `INDEXSUB_1` to `INDEXSUB_30`. Logic: split by adjacent-case.
       6.  `DATEOFF:OFFICEAB:AB_REFA:OFFICEC:C_REFA` -> 100 new columns (`DATEOFF_1`, `OFFICEAB_1`...`C_REFA_20`). Logic: split by ` : `.
       7.  For each `DATEOFF_{i}` (from 1 to 20) -> `DATEOFF_{i}_BEGINNING`, `DATEOFF_{i}_END`. Logic: split by `-`.
     - **Conditional Logic**:
       1.  For each record `i` from 1 to 20:
       2.  Create `ABC_REFA_{i}` by combining `C_REFA_{i}` and `AB_REFA_{i}` (preferring the value from `C_REFA_{i}`).
       3.  Create `OFFICE_TYPE_{i}` by taking the first character of `ABC_REFA_{i}`.
       4.  Create `OFFICEABC_{i}` by selecting the value from `OFFICEAB_{i}` if `OFFICE_TYPE_{i}` is 'A' or 'B', or from `OFFICEC_{i}` if it's 'C'.
