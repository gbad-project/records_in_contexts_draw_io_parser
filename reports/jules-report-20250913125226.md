# Architectural Review and Task Enrichment for P2T1: Draw.io Parser

**Date**: 2025-09-13
**Author**: Jules
**Task Reviewed**: P2T1 – XML to internal model

## 1. Objective

The primary objective of this architectural review was to analyze the unreviewed task P2T1 and enrich its description in `AGENTS.md`. The goal was to deconstruct the task of porting the Python `draw_io_parser.py` script into a detailed, actionable blueprint for a future TypeScript implementation, making the execution as straightforward as possible for the implementing agent.

## 2. Analysis Performed

To create a comprehensive blueprint, I performed a three-part analysis:

1.  **Core Logic Deconstruction**: I conducted a deep static analysis of the source Python script, `draw_io_parser.py`. This revealed a complex, multi-stage parsing process involving initial cell categorization, HTML parsing of cell values, and a geometric search algorithm for resolving un-locked arrow connections.

2.  **Test Oracle Reverse-Engineering**: I analyzed `tests/test_draw_io_parser.py`. The key finding was that the tests are high-level, end-to-end "golden file" tests that compare the final RDF output against a ground truth `.ttl` file. This identified the sample `.drawio` and `.ttl` files as the primary specification for the parser's required behavior. It also highlighted a lack of unit tests in the original implementation.

3.  **Real-World Data Inspection**: I inspected the two main `.drawio` files used in the tests. This confirmed that they use a consistent XML structure where semantic mapping information is encoded in the `style` and `value` attributes of `<mxCell>` elements. It also confirmed the heavy use of embedded HTML and IRI templates (e.g., `{PLACEHOLDER}`).

## 3. Task Enrichment of P2T1

Based on the analysis, I replaced the high-level description of P2T1 in `AGENTS.md` with a detailed, multi-step implementation plan.

### Rationale for New Breakdown:

The new breakdown is designed to guide the implementing agent through a logical, testable process, mitigating the risks discovered during the analysis.

*   **P2T1.1 - Define Core Data Structures**: Explicitly defining the `Individual`, `Arrow`, and `Literal` interfaces upfront establishes a clear data contract for the module.
*   **P2T1.2 - Implement Initial XML Parsing and Cell Categorization**: This isolates the initial, coarse-grained parsing of the XML file from the more complex logic, allowing it to be developed and tested independently.
*   **P2T1.3 - Implement HTML Value Extraction**: The original Python script used a custom HTML parser. By defining this as a separate sub-task, the agent is encouraged to create a dedicated, robust utility for this critical step.
*   **P2T1.4 - Implement Arrow Source/Target Resolution**: This is the most complex part of the parser. Isolating it as the final sub-task ensures that it can be built on top of a solid foundation of already-parsed and categorized data.
*   **Testing Strategy**: The new description explicitly mandates a unit-testing approach, which was missing in the original Python code. This will improve the robustness and maintainability of the new TypeScript module.

## 4. Potential Risks and Recommendations

*   **Complexity of Geometric Search**: The logic for finding the source/target of unlocked arrows is geometrically complex. The implementing agent should pay close attention to the Python implementation of `_cell_close_to` and write specific unit tests for this feature.
*   **HTML Parsing Edge Cases**: The embedded HTML in the `.drawio` files may have edge cases not immediately apparent. A robust HTML parsing utility is recommended over simple regex.

By following this detailed blueprint, the agent assigned to P2T1 should have a much clearer path to a successful implementation. The task is now considered architecturally reviewed and ready for development.
